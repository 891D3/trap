# BRD — Trap 个人工作台 业务需求文档

> 状态：**草案 v0.2**（2026-10-12 初建；v0.2 重构定位）

## 1. 背景

个人日常的工作、学习与兴趣爱好事务分散在多个工具中：待办在便签或 App 里、信息散落在浏览器标签页、灵感无处归档。缺少一个**常驻桌面、统一入口**的个人工作台，把这些事务沉淀为可管理、可回溯、可自动化的数字资产。

## 2. 产品定位

**Trap 是一个本地优先、AI Native 的个人效率与成长工作台**：

- 以**桌面应用**形态常驻运行，用户随时可见的数字化工作台；
- 围绕**工作、学习、兴趣爱好**三类事务，通过快速迭代持续生长功能；
- 数据 100% 本地；AI 能力以对话式 Agent 为入口，可操作工作台数据并驱动自动化流程。

**核心价值主张：**

1. **一切皆事务，事务可关联**：待办、信息、项目、快捷入口统一在一个界面内，用属性相互关联。
2. **AI Native**：对话式 Agent 入口（形态 2）+ Agent 自主流程（形态 3），机器做重复劳动，人做决策。
3. **本地优先**：所有数据保存在本机（SQLite + 本地文件）；AI 调用仅在用户显式触发时出网。
4. **可观察、可回溯**：数据看板呈现效率与成长轨迹；动态消息流汇聚全部事件。

## 3. 目标用户与场景

- **目标用户**：个人用户（首要为本产品作者本人），具备一定技术能力。
- **典型场景**：
  1. **随手记待办**：工作台常驻桌面，灵感/任务秒级录入，一键完成。
  2. **信息沉淀**：灵感、重要事项记录为 markdown，归档整理后可导出本地 `.md` 文件。
  3. **项目推进**：项目下分类事项明细与进度跟踪；事项可关联待办执行。
  4. **快速跳转**：常用工具/网站集中管理，一键直达。
  5. **AI 协作**（后续）：对话让 Agent 整理信息、拆解任务、驱动自动化流程。

## 4. 系统形态

### 4.1 界面信息架构（三栏布局）

```
┌──────────────┬───────────────────────────────┬───────────────┐
│ 左侧导航(可收起/展开) │   中间主功能区 (65%~80% 宽)    │  辅助区 (~20% 宽) │
├──────────────┼───────────────────────────────┼───────────────┤
│ ① 用户信息区  │ 主功能区（按左侧选中功能切换）：      │ · 日历         │
│   头像+姓名   │  · 待办列表（快速添加/打勾完成/删除） │ · 快捷便签      │
│   「{姓名}的工作台」│ · 信息记录（markdown 编辑/归档/导出）│ · 动态消息流   │
│ ② 工作台功能区 │  · 项目工作（进度+分类事项明细）     │               │
│   - 待办事项   │  · 快捷入口（工具/网站 CRUD+跳转）   │               │
│   - 信息记录   │  · 数据看板                        │               │
│   - 快捷入口   │                                   │               │
│ ③ 项目列表区  │                                   │               │
│ ④ 设置        │                                   │               │
└──────────────┴───────────────────────────────┴───────────────┘
```

- 左侧栏从上到下：用户信息区 → 工作台功能区 → 项目列表区 → 设置按钮；可收起/展开。
- 辅助区常驻：日历、快捷便签、动态消息流（消息流汇聚全部事件源：待办完成、信息变更、后续工作流事件等）。

### 4.2 技术架构

```
┌────────────────────────────────────────────────────┐
│ mygo 桌面应用（宿主：窗口/WebView/生命周期/自动更新）    │
├────────────────────────────────────────────────────┤
│ Go 应用层（Trap 本体，即「引擎」）：数据访问、存储、       │
│ （长期）工作流引擎                                     │
│   ↕ mygo typed IPC（已查证，2026-10-12）：             │
│   · mygo.Bind(service) → mygo generate 生成 TS 客户端    │
│   · mygo.NewEvent[T] + Emit/Broadcast：Go→前端类型化事件  │
│   · *mygo.Channel[T]：长任务流式回传                    │
│   · sqlite 插件（Go 侧直用，无 cgo）；fetch 插件（白名单）  │
│   ↕ 本地子进程管理                                      │
│ Node sidecar：内嵌 pi agent SDK（AI 能力底座，P2）        │
│   · customTools → 经 Go 应用层操作工作台数据              │
│   · 云端 LLM API（密钥本地保存，用户显式触发才调用）        │
├────────────────────────────────────────────────────┤
│ WebView 前端（React + TypeScript）                     │
│   三栏工作台 UI / Milkdown 编辑器 / 对话面板 / 看板       │
└────────────────────────────────────────────────────┘
```

> 查证记录：mygo（github.com/egoist/mygo）是 Go 桌面应用框架。其「插件」= Go 侧
> `mygo.Plugin{Name, Service}` + npm JS 包（官方插件：fetch/websocket/sqlite/updater/
> terminal/glass/game）。Trap 的业务代码直接作为 mygo 应用本体编写，无需自建 RPC/WS 协议。

### 4.3 关键架构决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 宿主 | mygo 桌面应用 | 复用窗口/WebView/typed IPC/自动更新；常驻桌面形态 |
| 引擎通道 | mygo typed IPC（Bind 服务 + Events 事件流 + Channel 流式） | 官方机制，`mygo generate` 生成 TS 客户端即类型事实源，无需自建协议 |
| 数据与业务逻辑 | Go 应用层 | 单机零部署、SQLite 稳定；前端不直接碰数据（AGENTS.md 引擎边界沿用） |
| AI 底座 | Node sidecar 内嵌 pi agent SDK | 复用成熟 agent 运行时（会话/工具/多 provider）；customTools 桥接 Go 应用层数据 |
| LLM 来源 | 云端 API | 能力优先；密钥本地保存，调用须用户显式触发 |
| 前端 | React + TypeScript（严格模式） | mygo WebView 生态（WKWebView/WebView2/WebKitGTK，均可跑 Milkdown） |
| 持久化 | SQLite（mygo sqlite 插件/Go 侧直用）+ 本地文件 | 结构化数据入库；信息记录正文为 markdown 文本；导出物/附件为本地文件 |
| markdown 编辑器 | Milkdown（Crepe） | markdown-first 所见即所得，`/` 菜单开箱即用，存储/导出零转换（对比 BlockNote：JSON 存储+转换层，偏重） |
| 自动更新 | mygo 内置更新机制（签名 + GitHub Releases + 增量更新） | 官方支持，Sparkle 式更新窗口；见 F8 |

### F1 工作台壳

- 三栏布局与左侧导航行为（收起/展开）如 4.1 节。
- 用户信息区：圆形头像（可更换）+ 姓名 +「的工作台」标题。
- 设置页：用户资料、主题、数据目录、AI 配置（密钥入口）、自动更新开关等。
- 多功能视图切换，切换状态与左侧选中项联动。

### F2 待办列表（P0）

- 快速添加：输入即加，回车提交；支持快捷键聚焦。
- 一键完成：点击打勾即完成；可取消勾选恢复。
- 删除：支持单条删除（删除需可恢复或二次确认，PRD 细化）。
- 属性（PRD 细化）：优先级、截止日期、所属项目关联（见 F5）。
- 待办是独立实体：不隶属项目；通过「项目关联」属性与项目事项建立联系。

### F3 信息记录（P0）

- 记录类型：灵感、重要事项等自由条目；支持归集与整理。
- 编辑器：**Milkdown（Crepe）**——markdown-first 的所见即所得编辑器（已确认选型，2026-10-12 讨论）：
  - 输入 `/` 呼出功能菜单插入 markdown 语法（标题、列表、引用、代码块、分割线、表格等），省去手动输入语法字符；交互风格对齐 Notion/Tolaria；
  - markdown 即数据本身：编辑内容为 GFM markdown 文本，无格式转换层。
- 表格支持：GFM 表格可视化编辑（`/` 插入、单元格编辑、增删行列、对齐设置）。**能力边界**（markdown 格式固有限制）：不支持合并单元格、单元格内嵌套块；如个别场景需合并单元格，以「导出文件内嵌 HTML 表格」兜底。
- 存储：条目数据存 SQLite，内容为纯 markdown 文本（与编辑器格式一致，零转换）。
- 导出：单条/批量导出为本地 `.md` 文件（目标目录在设置中选择），内容原样写出，无损。
- 归档/整理：支持把零散记录整理归档（分组/合集，PRD 细化）。
- 拟引入依赖（已确认）：`@milkdown/kit`、`@milkdown/crepe`（MIT 许可）。

### F4 快捷入口（P0）

- 条目：名称、URL（或本地工具路径）、图标、分组。
- 操作：添加、删除、修改；点击跳转目标地址（调系统浏览器/打开工具）。
- 展示：分组化网格/列表（PRD 细化）。

### F5 项目工作（P1）

- 项目：进度概览 + 分类事项明细。
- 项目事项可**应用到待办**（生成/关联待办）；关联关系通过属性字段维护。
- 进度口径（完成事项占比等）在 PRD 细化。

### F6 辅助区（P1）

- 日历：月视图，可标记待办截止/项目节点（PRD 细化）。
- 快捷便签：随手贴，独立于待办与信息记录，快速创建/置顶/删除。
- 动态消息流：汇聚全部事件源（待办完成、信息记录变更、后续工作流/AI 事件），按时间倒序展示。

### F7 数据看板（P1）

- 指标建议（PRD 细化）：待办完成趋势（日/周）、时间投入分布、项目进度总览、信息记录产出统计。

### F8 自动更新（P1）

- 机制：**复用 mygo 内置自动更新**（已查证，无需自研）：`mygo build` 对各平台构建签名，应用内 updater 插件下载新版本、对照内置公钥验签、替换应用；支持 GitHub Releases 与增量更新，带 Sparkle 式更新窗口。
- 发布流程：`mygo keygen` 生成签名密钥对；私钥仅存密码管理器与 CI secrets（丢失将无法再发布更新）；`mygo.config.ts` 配置公钥与 GitHub 仓库（Trap 自己的仓库）。
- 行为：后台检查新版本 → 更新窗口展示版本说明 → 用户确认安装并重启。
- 约束：下载源仅限本项目 GitHub 仓库；用户可关闭自动检查（PRD 细化开关位置）。

### F9 AI 助手（P2）

- **形态 2（对话式入口）**：常驻对话面板，Agent 经 customTools 操作工作台数据（增删查改待办、检索/整理信息记录、管理项目事项、打开快捷入口等）。
- **形态 3（自主流程）**：Agent 可执行多步自动化任务（如「汇总今日灵感并生成周报草稿」），关键变更前征求用户确认。
- 底座：Node sidecar 内嵌 pi agent SDK；会话历史本地保存。
- LLM：云端 API，多 provider 可配置；密钥经本地配置管理，不写入代码库与数据库。
- 边界：AI 调用必须用户显式触发；Agent 对数据的写操作需在 UI 可见（经引擎事件通道反馈）。

### F10 工作流引擎（长期）

- 原 BRD F1–F3 内容保留：DAG 画布编排、DAG 调度器、节点状态机、本地子进程执行器、审批卡点、事件日志回放恢复、实时运行可视化。
- 定位调整：作为底层自动化能力，与 AI 助手（F9）在引擎层汇合（Agent 可触发/编排工作流）。
- 详细需求见附录 A（原 v0.1 内容存档）。

## 6. 非功能需求

| 维度 | 要求 |
|---|---|
| 隐私与数据 | 数据 100% 本地（SQLite + 本地文件）；无遥测、无云同步。**AI 功能是唯一例外**：仅在用户显式触发 AI 调用时，相关上下文发送至用户配置的 LLM provider；其余任何时候引擎/应用不主动联网（自动更新检查除外，见 F8） |
| 性能 | 三栏 UI 首屏秒开；常规操作（加待办、保存记录）响应 < 100ms；事件到 UI 推送延迟 < 500ms |
| 可靠性 | 应用异常退出后数据无损（SQLite 事务）；markdown 导出与库内数据一致 |
| 安全 | 子进程/外部命令只能来自显式定义；AI 写操作经引擎校验；自动更新安装包必须校验来源与完整性 |
| 可维护性 | 协议 schema 单一事实源；SQL 只在 store 层；前端 TypeScript 严格模式 |

## 8. 风险与开放问题

**风险：**
- Node sidecar 引入 Node 运行时依赖（M3 前不影响）；需设计 mygo 应用拉起/管理 sidecar 的方式（子进程 + 本地通道，P2 PRD 细化）。
- 自动更新签名私钥管理：丢失将无法发布后续更新（私钥仅存密码管理器与 CI secrets）。
- （长期）子进程执行的跨平台差异；React Flow 大规模 DAG 渲染性能。

**开放问题（待逐条确认）：**
1. ~~mygo 插件机制与通信协议~~ **已关闭**（2026-10-12 查证官方仓库 github.com/egoist/mygo）：typed IPC（Bind/Events/Channel）+ 官方插件体系（fetch/websocket/sqlite/updater/terminal/glass/game），见 4.2/4.3。
2. ~~mygo 是否内置 GitHub Release 更新能力~~ **已关闭**：内置签名自动更新（updater 插件 + `mygo build` 签名 + 增量更新），见 F8。
3. ~~`/` 菜单编辑器选型~~ **已关闭**：选定 Milkdown（Crepe），见 F3；实现时需对照 Tolaria 验证默认样式/交互差异并微调。
4. AI Agent 的工具粒度与权限边界（哪些写操作允许 Agent 直接做、哪些需确认）——F9 PRD 时确认。
5. 用户资料（头像/姓名）存储位置与多用户是否需要支持（当前假设单用户）。
