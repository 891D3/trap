本单元结论先行：13 条 bug 中 7 条是布局/交互细节，根因不是「实现写错」，而是 规格颗粒度没到可判定的程度——UI 基线只描述了「有什么」，没定义「在哪里、对齐谁、空态是什么」。 真正的解法是让规格可执行、让 E2E 能判定布局，而不是靠 agent 更仔细。

类别含义bug 编号为什么会漏

B 类占 7 条、超过半数 —— 这是后续所有机制设计的出发点。

三、五个缺陷预防机制（按性价比排序）

1 E2E 从「数据链路」扩成「数据 + 交互 + 布局」三层 覆盖 A 类全部 + C 类部分 零新依赖

现状证据：e2e/m0_e2e.go（1347 行）断言口径是数据库（m0_e2e.go:883 断言 due_date、:899 断言落库），DOM 层只用 waitFor 等元素出现。分类单选 grep 命中 0，getBoundingClientRect / getComputedStyle 命中 0。

结果：数据对了但 UI 错了，测试全绿。bug 3、4、6、7、9、12 全部能在这个口径下通过。

改法：① 每个视图每个可点元素 E2E 必须真点一次并断言效果（分类单选点完断言 aria-checked === 'true'）；② 用 getBoundingClientRect() 断言相对关系；③ 加文本保真断言（bug 5 那类「保存后丢了」用全等比较）。

2 规格文档补「判定条件」列，把「我以为」变成「可对答案」 根治 B 类 7 条

现状：ui-baseline 是描述式写法（「分类圆点单选 + 取消/保存」）。建议每个组件补三项，写到能被测试直接引用：位置关系（和谁同一行 / 靠哪边 / 左对齐到谁）、空态（无数据显什么、对齐谁）、状态映射（展开态 → 箭头朝右，收起态 → 箭头朝左）。

配套：规格应带 web/src/style.css:xxxx 锚点，改样式时能立刻知道动了哪条规格。你和 agent 对同一句话理解不同，但一张图就懂——所以要把图变成可执行的判定。

3 修复 → 回归接进自动检查，不靠人记得 让 AGENTS.md §5 真正被执行

现状：没有 test 脚本、E2E 靠手动 npm run test:e2e，AGENTS.md §8 检查单靠自觉打勾。§5 已写「修 bug 必须先写复现测试」，但 13 条 bug 说明它没被执行。

改法：CI / pre-commit 跑 typecheck + go test ./... + npm run test:e2e 三关；修复流程加硬动作——先在清单里写清「复现测试路径」列，再动代码，写不出来说明还没理解 bug，不许修。

4 建「状态与生命周期」通用约定 治 C 类，防在每个新视图上重复犯错

C 类 4 条本质是三个反复出现的问题：

  • 视图切换 = 组件卸载（web/src/App.tsx:77-82 条件渲染）→ 输入态全丢。约定：所有用户输入态提升到 store 或 sessionStorage，切视图不丢。
  • 默认值污染数据（web/src/panels/views/TodoView.tsx:514 的 todo.category || 'work'）→ bug 10。约定：未分类是显式状态 ''，任何地方不得用 falsy 兜底成有值。
  • 保存字段口径（bug 5）→ 约定：编辑保存必须全量读回校验，title 不允许截断/重写。
5 提交前拿规格逐条对，而不是「再看一眼」 补目检轮次的漏

证据：v0.3.0 开发期有 12 笔 fix(目检) 提交（git log 00967e4–3e3375d），全是布局微调——当时靠「截图 → 看 → 改 → 再看」迭代，没有一层自动检查能替代眼睛。

现在 13 条里 7 条布局问题，说明目检轮次也漏了。功能完成后按 ui-baseline §5.x 逐条对（手里拿着规格文档），比凭印象看有效得多，因为「再看一眼」没有判定标准。

四、如果只做三件事

E2E 加布局/交互断言 getBoundingClientRect 相对关系 + 可点元素全覆盖。覆盖 A + C 类，零新依赖，当天可落地。
ui-baseline 每个组件补「位置关系 / 空态 / 状态映射」 根治 B 类——这是 7 条 bug 的源头，也是投入产出比最高的一项。
修 bug 流程加硬门槛：复现测试路径先落盘，再动代码 让 AGENTS.md §5 从纸面要求变成流程闸门。

四+、为什么这样做（含被否决的备选）

  • 把 bug 转成 E2E 断言，而不是转成文档说明：文档说明会被跳过，断言不会。13 条的「期望」列本身就是可断言的（如第 3 条「同一行 + 靠右 + 在按钮左侧」），修完搬进 E2E，该 bug 永久消失。
  • 先改规格文档，而不是先加更多测试：测试需要断言什么，取决于规格定义了什么。规格不补，测试只能把当前的模糊理解固化成代码，反而锁死错误。
  • 被否决：要求 agent「更仔细地目检」。没有判定标准的仔细不可复现，也无法在 CI 里验证；且已证明 12 轮目检提交仍漏了 7 条布局问题。
  • 被否决：为前端引入大型测试框架（如 Playwright）。现有 e2e/m0_e2e.go 已能在真实 WKWebView 里驱动页面与 typed IPC，扩断言即可；引入新框架违反「未经确认不引入第三方依赖」。
