## 为什么这样做（含被否决的备选方案）

- **方向修正记录**：最初按「Trap 连接外部 MCP server（客户端方向）」拟契约并写了首版评估；用户澄清「MCP 能力 = 外部 AI 能接入 Trap 进行调用和操作」后，按**服务端方向**重做契约与评估，客户端方向在 BRD F11 中仅一句声明排除。教训：AI native 项目里「MCP 支持」有双关（接入别人 vs 被别人接入），后续涉及 MCP 的表述一律先确认方向。
- 被否决：MCP 客户端方向（本轮不做，需求已明确单指对外暴露）；为 MCP 单开独立里程碑（并入 M3，F11 与 F9 无硬依赖可先行，避免里程碑碎片化）。
- 关键架构判断：能力暴露复用 M0 起定型的 Bind 服务层，不在 MCP 层重写业务；最大技术不确定点（MCP server 子进程与主进程并发访问 SQLite）列为 M3 PRD 首日并发冒烟，附备选架构（本地 IPC 回连 Go 服务层）。
- 安全边界先行设计：默认关闭、默认只读、写需显式开启、删除类不暴露——外部 AI 写用户数据的误操作风险必须由 Trap 侧把关，不依赖外部客户端审批行为。
