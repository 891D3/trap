# MCP 接入能力（Trap 作为 MCP 服务器）需求评估

> 日期：2026-10-13 ｜ 评估对象：新增「MCP 接入能力」（拟 BRD F11）：Trap 作为本地 MCP 服务器，让外部 AI 客户端接入并调用/操作工作台能力
> 结论先行：**价值高、技术路径清晰（复用 Bind 服务层 + 成熟 MCP SDK），建议纳入 BRD**，里程碑归属 M3（AI 能力阶段，可与 F9 AI 助手并行、无硬依赖）。M0 范围不受影响。
> 注：Trap 主动连接外部 MCP server 的「客户端方向」**不在本期需求内**（用户 2026-10-13 明确：MCP 能力即外部 AI 接入 Trap）。

---

## 1. 背景与价值评估

- Trap 定位为 **本地优先、AI Native 的个人工作台**（BRD §2）：数据沉淀为可管理、可回溯、可自动化的数字资产。MCP（Model Context Protocol，modelcontextprotocol.io）是外部 AI 客户端连接工具/数据源的事实标准——Claude Desktop、Claude Code、Cursor、pi 等主流 AI 入口均已内置 MCP 客户端。
- **在 Trap 内提供 MCP 接入能力，即 Trap 作为 MCP 服务器**：用户在自己惯用的外部 AI 客户端里，就能直接查询和操作 Trap 中的待办、信息记录、快捷入口等数据，无需切换到 Trap 界面。这让 Trap 从「一个 App」升级为「个人数字资产的开放接入点」，是 AI Native 定位下杠杆最大的能力之一。
- **价值点**：
  1. **入口前置**：日常对话即操作工作台（「把这段记到我的信息记录里」「今天待办还有哪些」），Trap 的日常使用频率随外部 AI 使用频率提升；
  2. **生态复用**：不为每个外部 AI 单独开发集成，一次 MCP server 实现覆盖所有 MCP 兼容客户端；
  3. **数据资产化**：Trap 数据可进入用户更庞大的 AI 工作流（与知识库、代码助手等组合），强化 BRD §1「数字资产」定位。
- **与既有需求的承接**：暴露的能力就是 M0 起定型的 Bind 服务层（Todo/Note/QuickLink/App），**不在 MCP 层重复实现业务**；F11 本质是给服务层加一个「外部协议面」。

## 2. 可行性评估（关键查证，2026-10-13）

### 2.1 MCP 协议与实现选型（查证 modelcontextprotocol.io 及 pi 客户端行为）

- **协议机制**：MCP server 通过 **stdio**（本地子进程）或 streamable HTTP 暴露 tools/resources；客户端按 `mcpServers` 配置条目（`command/args/env/cwd`）拉起并连接本地 server。**本机 stdio 模式与「数据 100% 本地」硬约束天然兼容**：连接与数据交换都发生在用户本机，不外发。
- **客户端侧事实**（查证 pi 文档 docs/mcp.md，佐证生态成熟度）：主流客户端以统一 `mcp.json` 格式配置本地 server（Claude Desktop/Cursor 条目可直接迁移）；工具命名 `mcp__<server>__<tool>`；客户端均把 MCP 调用纳入其工具权限管线（读写提示注解 `readOnlyHint`/`destructiveHint` 可供客户端权限层使用）。
- **Trap 侧实现路径**（具体选型在 MCP PRD 查证定稿）：
  1. **能力暴露**：把 Bind 服务层方法映射为 MCP tools——如 `list_todos` / `add_todo` / `set_todo_done` / `search_notes` / `create_note` / `export_notes` / `list_quick_links` 等；查询类映射只读方法，写类映射服务层写方法（校验逻辑全部复用，不在 MCP 层重写）；
  2. **MCP SDK**：官方 `@modelcontextprotocol/sdk`（TypeScript）或 Go 侧实现（如 `mark3labs/mcp-go` 等，届时查证对比）；官方 SDK 与 Node sidecar（F9 底座）同栈，**倾向官方 SDK 在 sidecar 进程内起 MCP server、经本地通道回连 Go 服务层**——避免双进程栈，具体架构在 PRD 定稿；
  3. **进程形态**：外部客户端经 stdio 拉起 Trap 的 MCP server 子进程；子进程需访问同一 SQLite 数据库——**多进程并发访问 SQLite 的锁策略是本功能最大技术不确定点**（mygo sqlite 插件 WAL 模式支持多连接读写，M3 PRD 需验证并写明并发约定）；
  4. **配置管理**：设置页提供「MCP 接入」区：总开关（**默认关闭**）、暴露范围选择（只读/读写）、客户端接入说明（生成用户可复制的 mcpServers 配置片段）。

### 2.2 安全边界（本功能的核心设计项）

- **默认关闭**：MCP 接入开关默认 off，用户显式开启后才存在 MCP server 进程。
- **暴露分级**：
  - 只读工具（查询待办/记录/入口、导出文件）：可直接暴露；
  - 写工具（增删改待办/记录/入口）：两种策略待 PRD 定稿——(a) 默认不暴露，用户显式开启「允许外部写」；(b) 暴露但外部调用方（AI 客户端）自身有审批机制时依赖其确认。**建议 (a) 起步**：安全边界由 Trap 侧掌控，不依赖外部客户端行为；
  - 高危操作（删除数据、打开外部目标）：**不暴露**（保留在 Trap 界面内完成）。
- **数据本地化**：stdio 通道不出网；开启 MCP 接入不改变「引擎不主动联网」约束。F11b 客户端方向（若未来要做）才涉及出网，本期排除。

### 2.3 可行性结论

**无阻塞项，但有一个必须前置验证的技术点**：多进程访问同一 SQLite（MCP server 子进程 ↔ Trap 主进程）。方案空间明确（WAL + 短事务 / MCP server 经本地 IPC 回调 Go 服务层），M3 PRD 首日做验证冒烟后定稿。

## 4. 依赖清单

- MCP SDK（官方 `@modelcontextprotocol/sdk`，TypeScript，MIT——倾向项）：**新第三方依赖**，M3 PRD 时按 AGENTS.md 硬约束单独申报理由并经用户确认；
- 其余复用既有栈（mygo 宿主、SQLite、事件通道、React 设置页），无新增 Go 依赖。

## 5. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| 1 | 多进程并发访问 SQLite（Trap 主进程 ↔ MCP server 子进程）数据竞争/锁等待 | M3 首日并发冒烟；备选架构「MCP server 经本地 IPC 回连 Go 服务层，SQL 单点在主进程」，代价是通道开发 |
| 2 | 外部 AI 写操作误删/误改用户数据 | 默认只读；写暴露需显式开启；删除类高危操作不暴露；每次外部操作写入动态消息流可回溯 |
| 3 | MCP server 子进程生命周期（客户端退出后残留） | stdio 由客户端拉起、客户端断开即退出（协议保证），主进程仅负责数据面；实现后 E2E 覆盖残留检查 |
| 4 | 官方 SDK 演进（协议仍在 2025-11-25 版本附近迭代） | 锁定 SDK 版本；工具面收窄到稳定核心（tools/resources），不追新特性 |
| 5 | 外部客户端配置门槛（用户需手写 mcpServers 条目） | 设置页生成可直接复制的配置 JSON + 接入向导说明 |

## 6. 开放问题（M3 PRD 时逐条确认）

1. 进程形态：MCP server 作为 sidecar 内嵌（官方 SDK）还是独立子进程（Go 实现）——取决于并发验证结果。
2. 写操作暴露策略：(a) 默认不暴露、显式开启 vs (b) 暴露 + 依赖客户端确认；删除类是否一律不暴露（评估建议：是）。
3. 首批工具清单：待办/记录/入口三域的最小工具集（建议每域 2–4 个，对齐 Bind 服务方法）。
4. MCP 接入与 F9 AI 助手的边界：外部 AI 写入的数据是否需要来源标记（建议：M1 信息记录已有来源概念时一并定）。
5. 里程碑内排期：与 F9 并行或先 MCP 后 AI（MCP 无硬依赖 F9，可先行）——用户在 M2 收尾时确认。

## 7. 结论与建议

- **通过评估**：MCP 接入（服务端方向）价值明确、路径清晰，建议立即纳入 BRD v0.3（新增 F11），里程碑归属 M3。
- **建议下一步**：BRD 升版 v0.3 → M0 PRD 补范围外与设置页占位 → MCP 详细 PRD 在 M3 开工前拆分（并发验证冒烟为 PRD 内首个确认项）。
